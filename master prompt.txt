# MASTER DEVELOPMENT PROMPT — ECOTRACE INDIA

================================================================================

## 1. OVERVIEW

================================================================================

Build **EcoTrace India**, a production-ready, full-stack, web-based **e-waste collection and reverse-logistics platform for India**.

EcoTrace is not merely an e-waste marketplace or consumer pickup application. It is a **digital coordination and traceability layer** connecting India's fragmented e-waste collection ecosystem.

The platform connects:

**CONSUMERS → COLLECTORS → LOCAL HUBS → FORMAL RECYCLERS → COMPLIANCE / EPR**

The product is designed around the reality that India already has a large informal collection network consisting of:

* Normal people
* Kabadiwalas
* Raddiwalas
* Ragpickers
* Junk collectors
* Local scrap dealers
* Independent field collection agents

The problem is that this existing network is fragmented, largely offline, inconsistent in pricing and grading, difficult to track, and poorly connected to formal recycling and compliance operations.

EcoTrace should digitally organize this existing ecosystem rather than attempt to replace it.

### Core Problem

Consumers often do not have a simple, transparent and trustworthy way to dispose of e-waste.

Collectors often operate with:

* Manual records
* Inconsistent weighing
* Inconsistent material classification
* Unstable pricing
* Limited access to organized collection opportunities
* Limited digital financial records

Formal recyclers face:

* Fragmented procurement
* Inconsistent material quality
* Difficult material traceability
* Weight discrepancies
* Logistics inefficiencies
* Operational leakage
* Compliance/documentation complexity

EcoTrace addresses these problems through one connected digital workflow.

### Core Value Proposition

EcoTrace should provide:

* Convenient e-waste collection
* Transparent category-based pricing
* Collector job discovery
* Digital weighing and grading
* Secure digital payments
* Local aggregation hubs
* Batch consolidation
* QR-based material tracking
* Recycler-side processing records
* EPR/compliance records
* Operational analytics
* Fraud/anomaly monitoring
* Environmental impact visibility

### Primary Workflow

Implement the following core lifecycle:

```text
Consumer
   ↓
Create Pickup Request
   ↓
Nearby Collector
   ↓
Collector Accepts Job
   ↓
Collector Visits Consumer
   ↓
Inspect + Weigh + Grade + Photograph
   ↓
Final Price Calculation
   ↓
Digital Payment
   ↓
Collector Delivers Material to Hub
   ↓
Hub Verifies Weight
   ↓
Inventory Updated
   ↓
Material Consolidated Into Batch
   ↓
Batch Sealed + QR / Manifest Generated
   ↓
Recycler Receives Batch
   ↓
Processing / Recovery Data
   ↓
EPR / Compliance Record
```

Every important material movement should be traceable.

## 3. DEVELOPMENT RULES

================================================================================

### General Principles

Build the application as a real product, not a generic CRUD demonstration.

Prioritize:

* Clear architecture
* Maintainability
* Readability
* Reusability
* Security
* Accessibility
* Responsive design
* Traceability
* Correct business logic

Do not over-engineer.

### TypeScript

Use TypeScript everywhere.

Enable strict TypeScript mode.

Do not use `any` unless absolutely unavoidable and explicitly justified.

Use:

* Interfaces/types
* Zod schemas
* Typed API responses
* Typed database operations
* Typed component props

### Frontend Architecture

Organize frontend features logically:

```text
features/
├── auth/
├── consumer/
├── collector/
├── pickups/
├── payments/
├── hubs/
├── batches/
├── recyclers/
├── epr/
├── notifications/
└── analytics/
```

Create reusable components for:

* Cards
* Tables
* Forms
* Dialogs
* Modals
* Status badges
* Buttons
* Empty states
* Loading states
* Error states
* Confirmation dialogs
* Charts
* Filters

### Backend Architecture

Follow:

```text
Routes
 ↓
Controllers
 ↓
Services
 ↓
Repositories
 ↓
Prisma
 ↓
PostgreSQL
```

Controllers must remain thin.

Business logic belongs in services.

Database operations should not be scattered throughout controllers.

### API Design

All APIs use:

```text
/api/v1/
```

Use consistent success and error responses.

Success:

```json
{
  "success": true,
  "message": "Operation successful",
  "data": {}
}
```

Error:

```json
{
  "success": false,
  "message": "Error message",
  "errors": []
}
```

### Financial Operations

Financial operations must be idempotent.

Every payment operation must use a unique idempotency key.

Prevent duplicate payments caused by:

* Page refresh
* Network retry
* Duplicate requests
* Queue retries

Financial history must be immutable.

### Auditability

Track important operations including:

* Registration
* Pickup creation
* Pickup assignment
* Weight changes
* Price changes
* Payment creation
* Payment status changes
* Batch creation
* Batch dispatch
* Batch receipt
* EPR record creation
* Admin pricing changes

Record:

* Actor
* Action
* Entity
* Entity ID
* Timestamp
* Previous value where relevant
* New value where relevant
* IP address where appropriate

Never hard-delete important operational or financial records.

### Validation

Validate on both:

* Frontend
* Backend

Never trust frontend validation alone.

Use Zod for shared validation wherever practical.

### Error Handling

Every major workflow must include:

* Loading state
* Success state
* Empty state
* Validation error
* API error
* Network error
* Permission error
* Retry option where appropriate

Do not expose stack traces or internal database errors to users.

### Logging

Use structured application logging.

Log:

* Authentication events
* API failures
* Payment events
* Background job failures
* Important state transitions
* Security events

Never log sensitive credentials or secrets.

### Testing

Test critical business logic including:

* Authentication
* RBAC
* Pickup creation
* Pickup claiming
* Weight validation
* Price calculation
* Payment idempotency
* Hub reconciliation
* Batch creation
* Pricing changes
* Status transitions

### Environment Variables

Never hard-code secrets.

Use environment variables for:

* Database
* JWT secrets
* Redis
* Payment provider
* Storage
* Maps
* Email
* AI services

### Responsive Design

The entire application must work across:

* Mobile
* Tablet
* Desktop

The collector experience must be especially optimized for mobile devices.

### Accessibility

Use:

* Semantic HTML
* Keyboard navigation
* Visible focus states

## 9. SECURITY

================================================================================

Security must be designed into the application rather than added later.

### Authentication

Use:

* JWT access tokens
* Refresh tokens
* HTTP-only cookies
* Secure cookies in production
* Short-lived access tokens

### Authorization

Implement server-side RBAC.

Never trust:

* Frontend role values
* Client-provided user IDs
* Client-provided ownership information

Every protected request must verify that the authenticated user has permission to access the requested resource.

### Password Security

Use:

* bcrypt or Argon2

Never store plaintext passwords.

### Session / Token Security

Implement:

* Token expiration
* Refresh token rotation where appropriate
* Secure cookies
* SameSite protection
* Logout/revocation strategy

### Rate Limiting

Use Redis where appropriate to protect:

* Login
* OTP
* Password reset
* Payment endpoints
* Public APIs
* AI endpoints

### CORS

Allow only configured trusted origins.

Never use unrestricted production CORS.

### Input Security

Implement:

* Schema validation
* Request size limits
* Safe database queries
* XSS protection
* Secure headers
* Helmet
* Appropriate CSRF protection
* Authorization middleware

### File Security

Never blindly trust uploaded files.

Validate:

* MIME type
* Extension
* Size
* User permission

Private documents must use:

* Signed URLs
* Expiring URLs
* Authorization checks

### PII Protection

Protect:

* Phone numbers
* Email
* Address
* Location
* UPI information
* Identity documents

Collectors should receive only the information necessary to perform a pickup.

Avoid exposing unnecessary consumer information.

### Payment Security

Never store:

* UPI PIN
* Card CVV
* Bank passwords
* Raw banking credentials

Verify payment webhooks through the payment provider's signature mechanism.

Use idempotency for payment operations.

### Audit Logs

Log security-sensitive and operationally significant actions.

Audit records should not be editable or hard-deleted.

### Data Deletion

Do not hard-delete:

* Payments
* Pickups
* Batches
* EPR records
* Audit records
* Wallet transactions

Use controlled status/archival mechanisms.

### AI Privacy

Minimize personally identifiable information sent to external AI services.

AI services should receive only the data necessary for classification or analysis.

## 11. AI RULES

================================================================================

AI should add genuine value but must never become a dependency for basic platform functionality.

If an AI service becomes unavailable:

**EcoTrace must continue operating through normal manual workflows.**

AI must assist humans rather than silently replace critical business decisions.

### AI FEATURE 1 — E-WASTE IMAGE CLASSIFICATION

#### Purpose

Assist collectors/operators in identifying e-waste material categories.

#### Input

A photograph of collected e-waste.

#### Possible Output

```json
{
  "category": "PCB_HIGH_GRADE",
  "confidence": 0.91,
  "suggestedGrade": "HIGH"
}
```

Potential categories:

* PCB
* Battery
* Display
* Appliance
* Plastic casing
* Metal
* Other electronics

#### Workflow

```text
Collector captures image
        ↓
Image uploaded
        ↓
AI analysis
        ↓
Prediction + confidence
        ↓
Collector/operator reviews
        ↓
Human confirms/corrects
        ↓
Final category recorded
```

AI must not automatically finalize high-value material transactions.

#### Failure Handling

If AI fails:

* Show manual classification
* Do not block collection
* Record AI service failure where useful

#### Logging

Store:

* Image reference
* Prediction
* Confidence
* Final human classification
* Timestamp

### AI FEATURE 2 — FRAUD / ANOMALY DETECTION

#### Purpose

Identify potentially suspicious patterns.

Potential signals:

* Unusually high weights
* Repeated identical images
* Unusual collection frequency
* Repeated high-value material claims
* Large collector/hub discrepancies
* Suspicious payment patterns
* Multiple accounts with similar information

#### Output

Create a fraud alert containing:

```text
Risk Score
Reason
Related Transaction
Related User
Relevant Metrics
Recommended Review Action
```

Never automatically ban or permanently penalize a user solely because of an AI prediction.

Human review is required.

### AI FEATURE 3 — PRICE ASSISTANCE

#### Purpose

Assist administrators with price suggestions.

Inputs may include:

* Historical transaction data
* Material category
* Regional pricing
* Configured price boundaries
* Available business data

AI should produce a suggested range.

It must not blindly determine the final financial price.

Final pricing must obey:

* Admin-defined minimum
* Admin-defined maximum
* Regional rules
* Material category
* Current business configuration

The exact price used in a transaction must always be stored.

### AI FEATURE 4 — ROUTE OPTIMIZATION

#### Purpose

Recommend efficient collector routes.

Optimize for:

* Distance
* Pickup time
* Collector capacity
* Vehicle capacity
* Geographic clustering
* Priority

The recommendation should remain understandable.

Do not make the collector interface dependent on an opaque AI recommendation.

### AI FEATURE 5 — ADMIN INSIGHTS

AI may analyze operational metrics to identify:

* Increasing e-waste supply regions
* Growing material categories
* Hubs with unusual losses
* Collectors with abnormal patterns
* High-demand pickup areas
* Material profitability changes

AI-generated insights must display supporting metrics whenever possible.

Do not present AI-generated conclusions as unquestionable facts.

### AI Rules

For every AI feature:

* Provide confidence where applicable
* Allow human override
* Log AI output
* Preserve uncertainty
* Handle failure gracefully
* Minimize PII
* Isolate AI modules from core business logic
* Never automatically perform irreversible financial actions based solely on AI
* Never make AI mandatory for core collection functionality

## 13. FINAL PRODUCT GOAL

================================================================================

Build **EcoTrace India** as a unified digital ecosystem that transforms fragmented e-waste collection into a structured, traceable and scalable reverse-logistics network.

The completed product should connect:

```text
INDIVIDUALS
     ↓
COLLECTORS
     ↓
LOCAL HUBS
     ↓
FORMAL RECYCLERS
     ↓
COMPLIANCE / EPR
```

while providing:

* Transparent category-based pricing
* Convenient e-waste pickup
* Collector job discovery
* Digital weighing
* Material classification
* Secure digital payments
* Collector earnings tracking
* Hub inventory management
* Batch consolidation
* QR-based material tracking
* Recycler processing records
* EPR/compliance-ready records
* Operational analytics
* Material-loss monitoring
* Fraud/anomaly alerts
* Environmental impact visibility
* Auditability
* Role-based access
* Privacy protection

The final application must feel like a **real startup product**, not a generic college CRUD project.

At the same time, the implementation must remain understandable enough for a college student to study, develop, test, demonstrate and deploy.

The system must prioritize the real business workflow:

```text
COLLECT
   ↓
WEIGH
   ↓
VALUE
   ↓
PAY
   ↓
AGGREGATE
   ↓
VERIFY
   ↓
BATCH
   ↓
RECYCLE
   ↓
TRACE
   ↓
REPORT
```

The central product principle is:

> **Do not build a new collection network from zero. Digitize, organize and connect the collection network that already exists.**

Technology should create **transparency, efficiency and trust** across the entire e-waste journey.

AI should augment human decision-making rather than replace it.

The architecture should be simple enough to build now, while creating a strong foundation for future expansion into larger collection networks, more hubs, more recyclers, advanced logistics, AI-assisted operations and broader compliance workflows.

The finished EcoTrace platform should therefore function as a single digital layer connecting **consumers, informal collectors, aggregation hubs, formal recyclers and compliance operations**, creating a traceable path from the moment e-waste is collected to the point where it enters formal recycling and associated records are maintained.
